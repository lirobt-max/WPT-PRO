# WPT Original – Windows Performance

## Project Overview: WPT Original (Windows Performance) is a portable Windows diagnostic and performance-restoration project designed to help a Windows PC reach a healthier, more reliable, and measurable operating state. Core Principles: Safety First: validate an action and its target before execution. Avoid unnecessary or destructive changes. Transparency: explain what the system is doing and keep meaningful logs. Measurability: collect baseline and post-run indicators so outcomes can be compared. Consistency: use a repeatable workflow and predictable interfaces. Continuous improvement: follow the PDCA cycle – Plan, Do, Verify, Improve. Architecture: intended workflow: 1. Bootstrap and environment checks. 2. Baseline data collection. 3. Diagnostics and servicing preparation in PowerShell 5. 4. Controlled handoff from PowerShell 5 to PowerShell 7. 5. Optimization and improvement tasks in PowerShell 7. 6. Post-run verification.  7. KPI comparison and reporting. Two engine PowerShell design: APSPW5 handles the initial diagnostic and servicing workflow and launches APSPW7. APSPW7 handles the subsequent optimization workflow. Measurement and Reporting: WPT aims to compare the computer’s condition before the engine run with its condition after the entire workflow completes. Candidate performance indicators include CPU utilization, RAM usage, disk measurements and available storage capacity, individual module execution time and total runtime, diagnostic findings and action outcomes. Metrics must be collected consistently. WPT must not report an improvement unless the before-and-after measurements support that conclusion. The final report should focus on two main measurement points: 1. Before Engine Run, 2. After Total Engine Completion. This approach provides a clear view of the overall outcome without confusing users with unnecessary intermediate measurements. WPT Event Journal: The WPT Event Journal is intended to serve as the central evidence record for significant actions, diagnostic findings, timestamps, errors, KPI data, and report generation. The journal should record important events and execution results, capture actionable error details, make failures visible rather than silently hiding them, support later analysis, database import, and report generation use a consistent event format and support configurable project paths instead of unnecessary hard-coded drive letters. Safety and Execution Expectations: validate required scripts, executables, paths, and permissions before launch, keep errors visible and record useful diagnostic details, don’t assume a command succeeded merely because it was launched, prefer reversible and narrowly scoped operations, avoid deleting personal data or critical Windows components without explicit authorization and a clear explanation. explain reboot requirements before restarting the computer, record meaningful execution results so actions can be reviewed. Safety, transparency, and reliability take priority over unsupported performance claims. Development Direction: the project focuses on the following development areas: engine architecture and interface consistency, environment validation, baseline performance collection, controlled PowerShell 5 to PowerShell 7 handoff, diagnostic and optimization workflows, WPT Event Journal implementation, KPI collection and comparison, final reporting, error visibility and execution verification, configurable paths and maintainable code. Development follows a structured, evidence-based process inspired by the PDCA improvement cycle: plan, do, verify, improve. Project status: this README describes the project’s intended architecture, principles, and development direction. It does not certify that every planned feature has been implemented or tested. Before any public release, verify supported Windows versions, required PowerShell versions, actual project folder structure, required permissions, exact operations performed by each engine, logging and error handling behavior, KPI measurement accuracy and known limitations, and tested results. Documentation should accurately reflect the current implementation. Safety, transparency, and measurable improvements are the primary goals.
